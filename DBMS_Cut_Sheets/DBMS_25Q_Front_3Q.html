[UI·Q1] Q. Define a database. Explain various applications of DBMS in detail. ★ Ans: Database: an organised, logically related collection of persistent data that describes an enterprise, stored with minimum redundancy and shared by many users and applications. DBMS = database + set of programs to define, create, query, update and control access to it (e.g. Oracle, MySQL, SQL Server, PostgreSQL). ★ Features: self-describing (catalog/metadata), data abstraction, multiple views, concurrent sharing, integrity, security, backup & recovery. ★ Applications: 1. Banking – customer accounts, deposits, loans, ATM/online transactions with ACID guarantees. 2. Airlines/Railways – reservations, schedules, seat availability (first users of distributed DBs). 3. Universities – student info, registration, attendance, grades, fees. 4. Sales/E-commerce – customers, products, orders, payments, recommendations. 5. Manufacturing – production, inventory, supply chain, orders. 6. HR – employees, salaries, payroll, tax deduction. 7. Telecom – call records, monthly bills, prepaid balances. 8. Finance/Stock market – share prices, trades, credit-card transactions. 9. Healthcare – patient records, prescriptions, billing. 10. Government & social media – Aadhaar, tax, census; posts, friends, likes. ★ Conclusion: DBMS is used wherever large volumes of shared data must be stored reliably and retrieved quickly.

[UI·Q3] Q. Describe the structure of a DBMS with a neat diagram. ★ Ans: DBMS is divided into modules; the two main components are the query processor and the storage manager. ★ ★ 1. Users: naive users (forms), application programmers, sophisticated users (query tools), DBA (schema, access, tuning). ★ 2. Query processor: DDL interpreter – processes DDL and records definitions in the data dictionary. DML compiler – translates DML into an evaluation plan of low-level instructions; query optimizer picks the lowest-cost plan. Query evaluation engine – executes the plan. ★ 3. Storage manager: interface between stored data and queries. Authorization & integrity manager – checks constraints and user rights. Transaction manager – consistency, concurrency control, recovery. File manager – space allocation on disk. Buffer manager – fetches pages into memory. ★ 4. Disk storage: data files, data dictionary (metadata), indices for fast access, statistical data for optimizer. ★ Working: query → parse & translate → optimize → evaluate → storage manager reads blocks → result.
[UI·Q4] Q. What is an ER diagram? Explain its components in detail. ★ Ans: ER diagram: graphical representation of the Entity–Relationship model (P. Chen, 1976) showing entities, attributes and relationships; used for conceptual design before tables are made. ★ ★ 1. Entity – real-world object (STUDENT); rectangle. Entity set – collection of similar entities. Weak entity – no own key, depends on owner (DEPENDENT of EMPLOYEE); double rectangle, identifying relationship = double diamond, partial key dashed underline. ★ 2. Attributes (ellipse): key – underlined (Roll_no); simple/composite (Name → First, Last); single/multivalued – double ellipse (Phone); derived – dashed ellipse (Age from DOB); stored. ★ 3. Relationship – association among entities; diamond (Enrolls). Degree: unary, binary, ternary. ★ 4. Mapping cardinality: 1:1, 1:N, M:1, M:N. ★ 5. Participation: total (double line – every entity participates) or partial (single line). ★ 6. Lines link attributes to entities and entities to relationships. ★ Uses: clear communication with users, easy conversion to relational tables.
[UI·Q5] Q. What is data independence? Explain its types with examples. ★ Ans: Data independence: the capacity to change the schema at one level of the database without changing the schema at the next higher level. Achieved by the three-schema architecture and mappings between levels. ★ ★ 1. Logical data independence: change the conceptual schema without changing external schemas or application programs. Examples: adding a column Email to STUDENT, adding a new table, splitting EMP into EMP_PERSONAL + EMP_PAY – old views still work through the external/conceptual mapping. Harder to achieve because programs depend heavily on logical structure. ★ 2. Physical data independence: change the internal schema without changing the conceptual schema. Examples: creating a B+ tree index on Roll_no, moving files to a new disk/SSD, changing heap file to hashed file, compression, changing block size – queries are unchanged; only conceptual/internal mapping changes. [UII·Q1] Q. Define a view. Explain how to create, modify and delete a view with SQL syntax and examples. ★ Ans: View: a virtual table defined by a stored query over one or more base tables; it stores no data itself – rows are computed when the view is used. ★ Create: CREATE VIEW view_name AS SELECT cols FROM table WHERE cond; Ex: CREATE VIEW cse_stu AS SELECT sid, name FROM student WHERE dept='CSE'; Query it like a table: SELECT * FROM cse_stu; ★ Modify: CREATE OR REPLACE VIEW cse_stu AS SELECT sid, name, cgpa FROM student WHERE dept='CSE'; (some DBMS: ALTER VIEW). ★ Update through view: UPDATE cse_stu SET name='Ravi' WHERE sid=101; – allowed only for simple views (one table, no GROUP BY, DISTINCT, aggregates, joins). WITH CHECK OPTION stops updates that would make rows leave the view. ★ Delete: DROP VIEW cse_stu; – removes definition; base table data stays. ★ Join view: CREATE VIEW emp_dept AS SELECT e.name, d.dname FROM emp e JOIN dept d ON e.did=d.did; ★ Advantages: security (hide columns like salary), simplicity (hide complex joins), logical data independence, customised data for different users, consistent results. Materialized view stores the result physically for speed.
[UII·Q2] Q. What are the different types of integrity constraints? Explain with examples. ★ Ans: Integrity constraints: rules on data that keep the database correct and consistent; checked by DBMS on every insert/update/delete. ★ 1. Domain constraint: each value must be atomic and from the attribute's domain/data type. age INT CHECK (age BETWEEN 17 AND 30). ★ 2. Key / entity integrity: primary key must be unique and NOT NULL. sid INT PRIMARY KEY – two students cannot share sid 101, sid cannot be NULL. ★ 3. Referential integrity: foreign key value must match an existing primary-key value in the referenced table or be NULL. did INT REFERENCES dept(did) ON DELETE CASCADE. Violations: inserting emp with did 9 when dept 9 is absent; deleting a referenced dept. Actions: RESTRICT, CASCADE, SET NULL, SET DEFAULT. ★ 4. NOT NULL: name VARCHAR(20) NOT NULL. 5. UNIQUE: email UNIQUE (allows one NULL). 6. CHECK: CHECK (salary > 0). 7. DEFAULT: city DEFAULT 'Hyd'. ★ 8. General / semantic constraints: assertions & triggers – CREATE ASSERTION e.g. total loans ≤ total deposits. ★ Example table: CREATE TABLE emp(eid INT PRIMARY KEY, name VARCHAR(20) NOT NULL, sal INT CHECK(sal>0), did INT REFERENCES dept(did));
[UII·Q3] Q. Explain the relational model in detail with its concepts. ★ Ans: Relational model (E.F. Codd, 1970): data is represented as a collection of relations (tables); simple, mathematical (set theory) and the base of SQL databases. ★ ★ Concepts: Relation – table of rows and columns. Tuple – a row (one record). Attribute – a column (named property). Domain – set of allowed atomic values of an attribute. Degree – number of attributes. Cardinality – number of tuples. Relation schema – R(A1,…,An), e.g. STUDENT(Sid, Name, Dept). Relation instance – set of tuples at a given time. NULL – unknown/not applicable value. ★ Keys: super key, candidate key (minimal super key), primary key, alternate key, foreign key, composite key. ★ Properties of relations: no duplicate tuples, order of tuples and attributes irrelevant, values atomic, each attribute name unique. ★ Integrity constraints: domain, key, entity integrity, referential integrity. ★ Operations: relational algebra / calculus, SQL (insert, delete, update, select). ★ Advantages: simplicity, structural independence, powerful query language, easy design via normalization.
[UII·Q4] Q. Explain Tuple Relational Calculus (TRC) and Domain Relational Calculus (DRC) with examples. ★ Ans: Relational calculus: non-procedural query language – states what to retrieve, not how. Based on predicate logic. ★ 1. Tuple Relational Calculus (TRC): variables range over tuples. Form: { t | P(t) } – set of tuples t for which predicate P is true. Uses ∧, ∨, ¬, ⇒, ∃ (there exists), ∀ (for all). ★ Ex 1: employees with salary > 50000: { t | t ∈ EMP ∧ t.sal > 50000 }. Ex 2: names only: { t.name | t ∈ EMP ∧ t.sal > 50000 }. Ex 3: students enrolled in course C1: { s.name | s ∈ STUDENT ∧ ∃e (e ∈ ENROLL ∧ e.sid = s.sid ∧ e.cid = 'C1') }. ★ 2. Domain Relational Calculus (DRC): variables range over attribute domain values. Form: { <x1, x2, …, xn> | P(x1,…,xn) }. ★ Ex 1: { <i, n, s> | <i, n, s> ∈ EMP ∧ s > 50000 }. Ex 2: names: { <n> | ∃i ∃s (<i, n, s> ∈ EMP ∧ s > 50000) }. ★ Safety: expressions must give finite results (e.g. { t | ¬(t ∈ EMP) } is unsafe).

[UIII·Q1] Q. Explain different types of SQL queries with syntax and examples. ★ Ans: SQL (Structured Query Language) – standard language for relational databases. Commands grouped into: ★ 1. DDL (Data Definition): CREATE TABLE student(sid INT PRIMARY KEY, name VARCHAR(20), dept CHAR(5)); ALTER TABLE student ADD email VARCHAR(30); DROP TABLE student; TRUNCATE TABLE student; RENAME. ★ 2. DML (Data Manipulation): INSERT INTO student VALUES(101,'Ravi','CSE'); UPDATE student SET dept='IT' WHERE sid=101; DELETE FROM student WHERE sid=101; ★ 3. DQL (Query): SELECT [DISTINCT] cols FROM tables WHERE cond GROUP BY cols HAVING cond ORDER BY col [ASC|DESC]; Ex: SELECT dept, COUNT(*) FROM student GROUP BY dept HAVING COUNT(*)>10 ORDER BY dept; Operators: BETWEEN, IN, LIKE 'R%', IS NULL, AND/OR/NOT. ★ 4. DCL (Control): GRANT SELECT, INSERT ON student TO user1; REVOKE INSERT ON student FROM user1; ★ 5. TCL (Transaction): COMMIT; ROLLBACK; SAVEPOINT s1; ROLLBACK TO s1; ★ Other queries: joins – SELECT e.name, d.dname FROM emp e INNER JOIN dept d ON e.did=d.did; set ops – UNION, INTERSECT, EXCEPT; nested queries; views.
[UIII·Q2] Q. Explain nested queries in SQL. Write examples of correlated and non-correlated queries. ★ Ans: Nested query (subquery): a SELECT written inside another SQL statement (in WHERE, FROM, HAVING or SELECT). Inner query result is used by the outer query. Operators: IN, NOT IN, =, >, ANY, ALL, EXISTS, NOT EXISTS. ★ 1. Non-correlated subquery: inner query is independent; executed once, result passed to outer query. ★ Ex 1: employees earning more than average: SELECT name FROM emp WHERE sal > (SELECT AVG(sal) FROM emp); ★ Ex 2: employees in Hyderabad depts: SELECT name FROM emp WHERE did IN (SELECT did FROM dept WHERE loc='Hyd'); ★ Ex 3: SELECT name FROM emp WHERE sal > ALL (SELECT sal FROM emp WHERE did=10); ★ 2. Correlated subquery: inner query refers to a column of the outer query; executed once for each outer row (slower). ★ Ex 1: employees earning more than their own dept average: SELECT e.name FROM emp e WHERE e.sal > (SELECT AVG(sal) FROM emp WHERE did = e.did); ★ Ex 2: depts having at least one employee: SELECT dname FROM dept d WHERE EXISTS (SELECT * FROM emp e WHERE e.did = d.did);

[UIII·Q3] Q. What is normalization? Discuss different normal forms with suitable examples. ★ Ans: Normalization: process of decomposing relations to remove redundancy and insert/update/delete anomalies, using functional dependencies (FDs), while keeping lossless join and dependency preservation. ★ ★ 1NF: all values atomic, no repeating groups. STUDENT(sid, name, phones='p1,p2') → one phone per row. ★ 2NF: 1NF + no partial dependency (non-key attribute depends on whole candidate key). R(sid, cid, sname, grade): sid→sname is partial → split STUDENT(sid, sname), ENROLL(sid, cid, grade). ★ 3NF: 2NF + no transitive dependency of non-key on key. EMP(eid, did, dname): eid→did→dname → EMP(eid, did), DEPT(did, dname). Rule: for X→A, X is super key or A is prime. ★ BCNF: for every FD X→Y, X is a super key. R(student, course, teacher), teacher→course violates → (teacher, course), (student, teacher). ★ 4NF: BCNF + no multivalued dependency (sid →→ hobby, sid →→ course split into two tables). ★ 5NF (PJNF): no join dependency; table cannot be decomposed further losslessly. ★ Advantages: less redundancy, consistency, smaller tables, easier maintenance. Drawback: more joins.
[UIII·Q4] Q. Explain triggers in SQL. Write a trigger for an INSERT or UPDATE operation. ★ Ans: Trigger: a stored PL/SQL block that runs automatically when a specified event (INSERT, UPDATE, DELETE) occurs on a table. Follows the ECA model – Event, Condition, Action. ★ Syntax: CREATE [OR REPLACE] TRIGGER trg_name {BEFORE | AFTER} {INSERT | UPDATE | DELETE} ON table [FOR EACH ROW] [WHEN (cond)] BEGIN statements; END; ★ Types: BEFORE / AFTER / INSTEAD OF (views); row-level (FOR EACH ROW, uses :NEW and :OLD) / statement-level (once per statement). ★ INSERT trigger – stop negative salary: CREATE TRIGGER chk_sal BEFORE INSERT ON emp FOR EACH ROW BEGIN IF :NEW.sal < 0 THEN RAISE_APPLICATION_ERROR(-20001,'Salary cannot be negative'); END IF; END; ★ UPDATE trigger – audit salary change: CREATE TRIGGER sal_audit AFTER UPDATE OF sal ON emp FOR EACH ROW BEGIN INSERT INTO emp_log VALUES(:OLD.eid, :OLD.sal, :NEW.sal, SYSDATE); END; ★ Testing: UPDATE emp SET sal=60000 WHERE eid=1; → a row is added to emp_log automatically. Drop: DROP TRIGGER sal_audit; ★ Uses: enforce complex integrity rules, auditing/logging, derived column values, automatic stock updates, security checks. Cautions: hidden logic, cascading triggers, performance overhead.
[UIII·Q5] Q. Describe aggregate functions in SQL. Discuss different types of constraints in SQL with examples. ★ Ans: Aggregate functions: compute a single value from a set of rows; usually with GROUP BY; NULLs ignored (except COUNT(*)). ★ COUNT – SELECT COUNT(*) FROM emp; SUM – SELECT SUM(sal) FROM emp; AVG – SELECT AVG(sal) FROM emp; MAX / MIN – SELECT MAX(sal), MIN(sal) FROM emp; ★ With GROUP BY / HAVING: SELECT did, AVG(sal) FROM emp GROUP BY did HAVING AVG(sal) > 40000; – WHERE filters rows before grouping, HAVING filters groups. COUNT(DISTINCT did) counts unique values. ★ Constraints in SQL: 1. NOT NULL – name VARCHAR(20) NOT NULL. 2. UNIQUE – email VARCHAR(30) UNIQUE. 3. PRIMARY KEY – unique + not null: eid INT PRIMARY KEY. 4. FOREIGN KEY – did INT REFERENCES dept(did) ON DELETE CASCADE. 5. CHECK – CHECK (age >= 18). 6. DEFAULT – city VARCHAR(10) DEFAULT 'Hyd'. ★ Table-level: CREATE TABLE enroll(sid INT, cid INT, PRIMARY KEY(sid,cid), FOREIGN KEY(sid) REFERENCES student(sid)); ★ Add/remove later: ALTER TABLE emp ADD CONSTRAINT c1 CHECK(sal>0); ALTER TABLE emp DROP CONSTRAINT c1; ★ Constraints keep data valid; aggregates summarise data for reports.
[UIV·Q1] Q. Explain the concept of a transaction in DBMS. Discuss ACID properties in detail. ★ Ans: Transaction: a logical unit of work – a sequence of read/write operations that must execute completely or not at all. Ex: transfer ₹500 from A to B: read(A); A=A−500; write(A); read(B); B=B+500; write(B); commit. ★ ★ States: active → partially committed (last statement done) → committed; on error → failed → aborted (rolled back, then restart or kill). ★ ACID properties: A – Atomicity: all operations or none; if failure after write(A), A's change is undone. Ensured by recovery manager (logs, undo). ★ C – Consistency: a transaction takes the DB from one consistent state to another; A+B stays the same before and after. Responsibility of programmer + integrity constraints. ★ I – Isolation: concurrent transactions don't see each other's intermediate results; result equals some serial order. Ensured by concurrency-control manager (locks, timestamps). ★ D – Durability: once committed, changes survive crashes. Ensured by recovery manager (write-ahead log, redo, stable storage). ★ Operations: read(X), write(X), commit, rollback. Problems without ACID: lost update, dirty read, unrepeatable read, inconsistent data.
[UIV·Q2] Q. What is serializability? Explain conflict and view serializability. ★ Ans: Schedule: order of execution of operations of concurrent transactions. Serial schedule – one transaction after another (always correct). Serializability: a non-serial schedule is serializable if its effect equals some serial schedule – ensures consistency with concurrency. ★ 1. Conflict serializability: two operations conflict if they belong to different transactions, access the same item and at least one is a write (R-W, W-R, W-W). A schedule is conflict serializable if it can be turned into a serial schedule by swapping non-conflicting adjacent operations (conflict equivalent). ★ Test – precedence graph: node per transaction; edge Ti → Tj if an operation of Ti conflicts with and precedes one of Tj. Acyclic ⇒ conflict serializable; topological order gives the serial order. ★ ★ 2. View serializability: S is view equivalent to serial S' if (i) same initial reads, (ii) same read-from (Ti reads value written by Tj in both), (iii) same final writes. Every conflict-serializable schedule is view serializable, not vice-versa – schedules with blind writes (write without read) may be view but not conflict serializable. Testing view serializability is NP-complete.

[UIV·Q5] Q. Describe the implementation of atomicity and durability in DBMS. ★ Ans: Recovery system implements atomicity (undo incomplete transactions) and durability (redo committed ones) after failures – transaction errors, system crash, disk failure. ★ Storage types: volatile (RAM), non-volatile (disk), stable storage (replicated copies – never lost; holds the log). ★ 1. Shadow copy / shadow paging: transaction updates a new copy of the database (or pages); a db-pointer points to the current copy. On commit, pages are flushed and pointer switched atomically; on abort, the new copy is discarded. Simple but costly for large DBs, causes fragmentation. ★ 2. Log-based recovery: log records on stable storage: <Ti start>, <Ti, X, old, new>, <Ti commit>, <Ti abort>. Write-Ahead Logging (WAL): log record written to stable storage before the data page. ★ Deferred update: writes applied only after commit → only redo needed. Immediate update: writes applied before commit → undo (using old values) for transactions without commit, redo (new values) for committed ones. ★ 3. Checkpoints: periodically flush log and dirty pages and write <checkpoint L>; recovery scans only from the last checkpoint – faster. ★ Recovery steps: redo phase (forward scan, repeat history) → undo phase (backward scan, roll back incomplete, write <Ti abort>). ★ Algorithm example: ARIES. Disk failure handled by archival backup + log.
[UV·Q1] Q. Explain different types of file organization in DBMS with their advantages and disadvantages. ★ Ans: File organization: the way records are placed in blocks of a file on disk; decides speed of insert, search, delete. ★ 1. Heap (pile) file: records inserted at the end wherever space exists. Adv: fast insert, good for bulk load. Disadv: linear search O(n), wasted space after deletes. ★ 2. Sequential (sorted) file: records stored in order of a search key. Adv: fast range & ordered access, binary search. Disadv: insertion/deletion costly (re-sorting, overflow blocks). ★ 3. Hash file: hash function h(key) gives bucket address. Adv: very fast equality search O(1). Disadv: poor for range queries, collisions/overflow, bucket skew. Static and dynamic (extendible, linear) hashing. ★ 4. Indexed sequential (ISAM): sorted file + index. Adv: both random and sequential access. Disadv: overflow chains, extra space. ★ 5. B+ tree file: records in leaves of a balanced tree. Adv: dynamic, balanced, good for equality and range. Disadv: complex, overhead. ★ 6. Clustered file: related records of several tables stored together (emp with dept). Adv: fast joins. Disadv: slow for single-table scans.

[UV·Q2] Q. Explain insertion in a B+ tree with an example. ★ Ans: B+ tree: balanced multi-level index; all keys in leaf nodes, internal nodes only guide search; leaves linked for range queries. Order n: each node holds ≤ n−1 keys and ≤ n pointers; nodes (except root) at least half full. ★ Insertion algorithm: 1. Search down from root to the correct leaf. 2. If leaf has space, insert key in sorted order. 3. If leaf is full, split: keep first ⌈n/2⌉ keys, move rest to a new leaf, copy the first key of the new leaf up to the parent; link leaves. 4. If parent overflows, split the internal node and move (push) the middle key up. 5. If root splits, a new root is created – tree height grows by one (grows at root, stays balanced). ★ Example (order 3, max 2 keys): insert 5, 10 → leaf [5|10]. Insert 15 → [5|10|15] overflows → split [5] and [10|15], copy 10 up → root [10]. Insert 20 → [10|15|20] splits → [10], [15|20], copy 15 → root [10|15]. Insert 25 → [15|20|25] splits → [15], [20|25], copy 20 → root [10|15|20] overflows → internal split, 15 moves up: new root [15], children [10] and [20]; leaves [5] [10] [15] [20|25]. ★ ★ Properties: search/insert O(log n), all leaves at same level, efficient range search through linked leaves. Used in almost every DBMS index.

[UV·Q4] Q. Explain Indexed Sequential Access Method (ISAM) with its structure. ★ Ans: ISAM (Indexed Sequential Access Method): static, tree-structured index developed by IBM; data file kept sorted on key with a multilevel index above it – supports both sequential and direct (random) access. ★ ★ Structure: 1. Primary data pages (leaf level) – records sorted by key, allocated sequentially when the file is created. 2. Index pages – non-leaf levels holding (key, pointer) entries that direct the search; built once and never change. 3. Overflow pages – inserts that don't fit in the proper primary page go to chained overflow pages. ★ Search: start at root, compare keys, follow pointers down to the leaf page, then scan it and its overflow chain. Cost ≈ logFN + overflow length (F = fan-out, N = no. of leaf pages). ★ Insert: find the leaf; if space, insert; else add to overflow page. Delete: remove from page; empty overflow page is freed, but primary pages stay (index not changed). ★ Advantages: simple, fast search when few updates, good sequential processing, no locking of index pages (static) → high concurrency. ★ Disadvantages: long overflow chains after many inserts → slow search, unsorted overflow, wasted space; periodic reorganisation needed. Hence replaced by dynamic B+ trees.
[UV·Q5] Q. Explain how data is stored on external storage devices in DBMS. ★ Ans: DBMS stores data on external (secondary) storage – mainly magnetic disks/SSDs, tapes for archive – because it is non-volatile, cheap and large. Data must be brought into main memory to be processed. ★ Storage hierarchy: cache → main memory → flash/SSD → magnetic disk → optical disk → tape (speed ↓, capacity ↑, cost/byte ↓). ★ Magnetic disk: platters with tracks, divided into sectors; cylinder = same track on all surfaces; read/write heads on an arm. Access time = seek time + rotational latency + transfer time. Data read/written in blocks (pages) – unit of I/O; DBMS minimises I/Os. ★ ★ Components: Disk space manager – allocates/deallocates pages, tracks free space. Buffer manager – keeps pages in a buffer pool in RAM; on request, returns the page or reads it from disk; uses pin count and dirty bit; replacement policies LRU, MRU, clock. ★ Records in pages: fixed-length or variable-length records; slotted page with slot directory; record id (RID) = (page id, slot no). ★ Files of records: heap, sorted, hashed files built from pages; indexes for access. ★ RAID: striping + mirroring/parity for speed and reliability (RAID 0, 1, 5). Tapes give sequential-access backup.
